# 내부 거래 완료와 소유권 이전 연결

A 시나리오의 예약 수락·양측 완료 확인을 정식 ownership/history/document 저장 구조에 연결한다. 기존 `PurchaseRequestService`와 `TradeCompletionService`의 권한·최신 버전·이력 확인을 유지한다.

## 처리 흐름

1. 구매 요청 수락에서 `InternalTradeOwnershipService.createPending`을 호출한다. 실제 요청·판매글·채팅방·양측 사용자·현재 소유권이 일치하는 RESERVED 관계만 허용한다.
2. 같은 트랜잭션에서 INTERNAL/PENDING 이전을 한 건 만들고 감사를 저장한다. 원문 토큰·링크·QR을 발급하지 않는다. 내부 예약은 자동 만료하지 않으므로 기존 NOT NULL `expires_at`에는 먼 미래 값을 저장한다. 만료된 DIRECT 요청만 대기 슬롯에서 정리한다.
3. 양측은 현재 공개 제품 정보와 이력에 대한 `factsVersion`을 각각 확인한다. 한쪽만 확인하면 RESERVED를 유지한다. 새 이력으로 버전이 달라지거나 미확인 변경이 있으면 완료하지 않는다.
4. 마지막 확인에서 기존 거래 서비스가 거래 COMPLETED·판매글 SOLD·다른 PENDING 요청 REJECTED를 저장하고 정식 완료 포트를 호출한다.
5. 완료 포트가 실제 양측 확인·요청·판매글·내부 이전 관계를 다시 검사한다. 이전을 COMPLETED로 확정하고 제품 소유자 변경·사실 버전 1 증가·시스템 TRANSFER 이력·증빙 보호를 처리한다.
6. 같은 트랜잭션의 `OwnershipTransferred`로 이전 작성자의 초안·사진 선택을 정리한다. 소유권·거래 감사까지 성공해야 커밋하며, 어느 단계의 실패도 전체를 되돌린다.

상위 거래 서비스의 제품 → 판매글 → 구매 요청 잠금을 유지한다. 정식 포트는 `Propagation.MANDATORY`로 독립 호출을 거부한다. 요청에 연결된 이전 행이 중복되거나 다른 제품·사용자·유형이면 성공으로 처리하지 않는다. 제품 잠금과 기존 제품별 PENDING 유일 슬롯, 시스템 이력의 `transfer_request_id` 유일 제약을 재사용한다.

완료 재요청은 원래 당사자의 저장된 결과를 반환한다. 후속 소유권 이전·보관 여부와 무관하게 기존 완료가 재실행되지 않으며, 시스템 이력·버전 증가·감사·새 소유자의 초안 삭제가 반복되지 않는다.

## 공개 종료와 승계

- 공개 API는 현재 소유권과 ACTIVE/RESERVED 판매글을 계속 검사한다. main의 정식 이력 마이그레이션이 추가한 `product_events.visibility`도 내부 거래 완료와 같은 트랜잭션에서 PRIVATE로 맞춘다. 이 PR은 별도 공개 컬럼이나 마이그레이션을 추가하지 않는다.
- SOLD가 되면 일반 판매글 상세·공개 이력·Q&A·AI 요약 제공이 종료된다. 생성 중이던 결과도 소유권·상태 재검사에 실패해 공개·저장되지 않는다.
- 새 소유자는 제품 화면에서 누적 이력과 마스킹 증빙을 계속 조회한다. 증빙의 업로더·파일은 바꾸지 않고 `protected_at`을 보존 또는 설정한다. 재마스킹 필요 상태도 해제하지 않는다.
- 정식 ownership DDL의 완료 상태인 COMPLETED를 사용한다. 기존 마이그레이션이나 상태 enum을 요구사항 문서의 ACCEPTED 표기에 맞춰 임의 변경하지 않는다.

## 내부 거래와 외부 링크 경계

외부 이전 생성 API는 클라이언트가 보낸 `purchaseRequestId`를 거부한다. 내부 구매 요청의 연결 대상은 거래 서비스가 정한다. 또한 INTERNAL 요청은 외부 링크의 조회·수락·취소 API로 처리할 수 없다. 내부 취소·완료는 P3/P4에서 거래·판매글과 함께 처리해야 한다.

## 내 거래 화면

- 판매글 상세의 구매자용 채팅 문의 버튼을 실제 대화방 생성·조회와 연결했다. 본인 글·비로그인·조회 실패에는 숨기고, 계정 변경 시 이전 클릭 연결도 정리한다. 구매 예약 요청은 이어서 내 거래 화면에서 진행한다.
- 구매 요청 조회에 SENT/RECEIVED 방향을 보내 역할을 구분하고 구매 요청 생성 URL을 정식 `/api/v1/market/listings/{listingId}/purchase-requests`로 맞췄다.
- 기존 내부 거래의 외부 링크 발급 버튼을 제거하고 `completion-context` 조회 → 현재 정보·이력 확인 → 내 완료 확인으로 연결했다. 판매자에게는 양측 확인 시 소유권 이전이 진행됨을 알린다.
- 확인 저장 후 상대 대기·최종 완료를 표시한다. 폴링에서 같은 내용이면 확인 입력·펼친 정보·포커스를 유지하고, 사실 버전이 달라지면 확인을 해제한다.
- 구매자는 미확인 변경을 확인하고 KEEP을 선택할 수 있다. 변경 목록은 페이지로 조회한다. 예약 취소는 기존 P3의 네 가지 enum 사유를 사용한다.
- 중복 제출, 다른 방으로 전환된 뒤 늦게 도착한 응답, 계정 변경을 처리한다. 휴대폰에서는 대화 목록과 선택한 대화를 나눠 표시한다. 새 동적 내용은 `textContent`로 표시한다.
- 상단 중고거래의 하위 메뉴가 좁은 화면에서 숨겨지거나 가로 스크롤 영역에 잘리지 않도록 수정했다. 마우스·클릭·키보드로 펼치고 내 거래·채팅으로 이동할 수 있다.

## 설정과 적용 범위

P2·P3·P4와 정식 이력 기능을 켠 환경에서 사용한다. 일반 설정의 기본 플래그는 변경하지 않았다. 새 DDL·라이브러리는 없으며 기존 pending P2/P3 SQL도 일반 마이그레이션 경로로 옮기지 않는다.

빈 DB에서는 정식 `db/migration`을 먼저 적용한 뒤 pending P2/P3를 별도로 적용해야 한다. P3 버전이 정식 history보다 앞서므로 세 경로를 처음부터 숫자 순서로 함께 적용하면 history FK 생성이 실패한다. 시험은 별도 DB·스키마에서 정식 마이그레이션 후 기존 pending 경로를 `outOfOrder=true`로 적용했다. 공유 DB에는 이 작업으로 마이그레이션을 실행하지 않는다.

- 수락 준비 실패, 이전·소유자·이력·증빙·양쪽 감사의 각 저장 후 실패, 초안 삭제 실패의 전체 롤백과 재시도를 확인했다.
- 양측 동시 확인, 취소/완료 경합, 새 이력의 재확인, 완료 재요청, 외부 링크 우회 차단과 실제 이전 뒤 늦은 AI 요약·Q&A 결과 차단을 확인했다.
- 18082 복제 DB 서버에서도 실제 로그인·인증 쿠키·CSRF로 판매자 확인 → 구매자 확인 → 완료를 실행했다. 소유자 변경·SOLD/COMPLETED·초안 삭제·시스템 이력 단일성과 공개 접근 종료, 새 소유자의 제품 접근을 확인했다. 기존 판매글 3번의 RESERVED 상태는 유지했다.

- 자동 브라우저의 클릭 시연·화면 및 휴대폰 렌더링 검증은 조작 연결 오류로 수행하지 못했다. 사용자 수동 테스트는 2026-10-30 완료 보고를 받았다. 자동 검증 결과와 사용자 확인을 구분하며, 모든 화면 크기의 검증을 의미하지는 않는다.

## PR #64 리뷰 보완

- 목록 조회 세대와 방별 조회 범위를 사용해 계정·방 변경 전의 성공·오류·401 응답을 차단한다. 이전 요청은 취소하며 각 API에는 15초 제한을 둔다. 폴링의 busy 상태는 각 폴링이 소유하므로 이전 finally가 새 방을 변경하지 않는다.
- 문의 POST와 목록 조회 뒤에도 같은 계정·판매글·이동 요청인지 확인한다. 거래 완료 후 도착한 조회나 과거 예약 상태는 완료 화면을 되돌리지 않는다. 제품 정보·변경 이력은 같은 최신 조회의 결과만 함께 반영한다.
- 메뉴가 닫힐 때 내부 포커스를 상위 버튼으로 돌린다. 아래 공간이 부족하면 위로 열고 아주 낮은 화면에서는 뷰포트 안에 스크롤 높이를 확보한다. 모바일 대화에서도 판매 가격 영역을 유지한다.
- PostgreSQL 기동 전 실패에도 시험 스키마를 정리하도록 연결을 별도로 보관한다. H2 기본 검사 두 건으로 컨텍스트가 없는 실패 정리와 정리 실패 시 컨텍스트 닫기를 검증했다. 실제 PG 시험은 최신 main 통합 후 25건 통과했으며 승계된 이력 601·문서 501이 응답에 존재하는지 검사한다.
- 기본 CI에 Node 대역 DOM 검사와 별도 PostgreSQL 통합 작업을 추가했다. 원격에서 이 새 작업의 실행 여부는 후속 푸시 후 확인해야 한다.
- Node 기본 시험기로 실제 JS 모듈의 지연 응답·화면 갱신을 20건 검사했다. 수정 전 커밋에서는 15건 실패·1건 시간 초과·4건 성공, 수정 후에는 20건 모두 성공했다. 이 검사는 실제 브라우저 렌더링을 대신하지 않는다.
- 함수의 역할과 상태·권한 경계를 짧은 Javadoc/JSDoc으로 보충했다. CodeRabbit의 주석 커버리지 재측정은 후속 PR 검토에서 확인한다.

## 최신 main 충돌 정리

- main의 전체·판매글별 공유 채팅 목록과 페이지 이동·판매자 상세 진입·읽음 표시·중복 전송 방지를 유지했다. 기존 사이드바 진입도 유지하며 PR의 상단 메뉴 펼침 보완을 함께 적용했다.
- PR의 거래 완료 확인·예약 취소·역할별 예약 API와 계정·방별 조회 취소·세대 검사를 공유 목록 흐름에 결합했다. 첫 HTML 로드가 늦는 경우도 판매글별 진입 대상을 보존한다.
- 충돌 텍스트 외에도 정식 이력의 PUBLIC→PRIVATE 메타데이터를 소유권 이전에 연결하고, 이 저장 직후 실패의 전체 롤백·재시도 검사를 추가했다. main의 이력 마이그레이션은 수정하지 않았다.
- Node 대역 DOM 검사는 공유 목록과 상세를 함께 실행하는 29건으로 확장해 모두 통과했다. 판매글별→전체 범위 전환, 20건 이후 목록 접근, 최초 지연 로드, 읽음·전송, 판매자/구매자 상세 진입을 추가 확인했다. 실제 브라우저 렌더링 시험과 구분한다.
