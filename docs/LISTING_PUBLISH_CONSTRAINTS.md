# 게시 전 거래·소유권 이전 검사

SALE-07에 따라 진행 중인 거래나 소유권 이전 요청이 있는 제품의 신규 게시를 막는다. 일반 local/운영 설정의 `ListingPublishConstraints`는 항상 허용하던 기본값 대신 실제 JDBC 조회를 사용한다. 시연 프로필의 샘플 구현은 유지한다.

## 호출 흐름

`POST /api/v1/products/{productId}/listings`
→ `ListingPublishService.publish`
→ 현재 소유권 확인·제품 행 잠금
→ 기존 게시 재시도와 초안 버전 검사
→ `JdbcListingPublishConstraints.inspect`
→ 사진·공개 예정 이력 재검사
→ 게시 저장·초안 정리.

| 원천 상태 | 신규 게시 |
|---|---|
| 같은 제품의 어느 판매글이든 `purchase_requests.transaction_status=RESERVED` | 409 `SALE_003` |
| 같은 제품의 `ownership_transfers.status=PENDING`, 만료 시각이 현재 이상 | 409 `SALE_003` |
| 수락 전 구매 문의 `PENDING`, 완료·취소된 거래 | 이 검사 통과 |
| 만료된 PENDING 또는 완료·취소·만료 처리된 이전 | 이 검사 통과 |
| 다른 제품의 거래·이전 | 영향 없음 |
| 필요한 테이블·컬럼이 없음 또는 조회 장애 | 503 `SALE_004` |

만료 시각과 현재 시각이 같을 때는 기존 `OwnershipTransfer.isExpired`와 같이 아직 유효한 것으로 본다. 검사는 이전 상태·토큰·만료 시각을 수정하지 않는다. 차단 시 판매글·사진·감사 기록을 새로 만들거나 초안을 삭제하지 않는다. 게시 응답을 잃어 같은 초안 ID·버전을 재전송하면 기존 멱등 응답을 유지한다.

## 동시 요청

- 게시와 외부 이전 발급 모두 제품 행을 먼저 잠근다. 게시가 먼저 확정되면 이전 발급은 ACTIVE/RESERVED 글을 확인하고 409 `OWN_005`를 반환한다. 이전 발급이 먼저 확정되면 게시가 409 `SALE_003`으로 거부된다.
- 이전 수락·취소도 제품→이전 요청 순서로 잠근다. 제품 ID만 먼저 조회하고 잠금 뒤 실제 이전 엔티티를 읽어, 대기 중 이전의 오래된 상태가 영속성 컨텍스트에 남지 않게 한다. 발급자·수신자·만료·현재 소유권의 기존 검사는 유지한다.
- 구매 요청 수락 경로는 기존 `JdbcPublishedListingAccess`의 제품→판매글→구매 요청 잠금을 사용한다. 이 작업에서 거래 상태 전이나 내부 이전 writer를 새로 구현하지 않는다.

## 스키마와 범위

정식 소유권 스키마는 기존 `2803·2804`, 거래 원천은 팀 P2의 `purchase_requests`이다. P2 DDL은 현재 `db/pending/trade-p2`에 있으므로, 일반 `db/migration`만 적용한 DB에는 거래 테이블이 없을 수 있다. 이때 게시를 허용하지 않는다. 자동 기능 플래그만 켜거나 DB가 비었다고 가정해 우회하지 않는다.

기존 마이그레이션 수정·pending DDL의 운영 승격·실제 개발 DB 변경은 하지 않는다. 거래 DDL의 정식 이행은 해당 담당자의 배포 계획과 맞춰야 한다. 테스트의 PostgreSQL 격리 스키마에만 기존 P2 DDL을 적용한다. H2 테스트의 최소 구매 요청 테이블은 읽기 계약용 시험 fixture다.

이 변경은 게시 조건 검사까지다. 게시/중지의 실제 이력 공개 처리, 판매중지와 거래 취소의 전체 연결, 소유권 이전 시 제품 버전·AI 갱신은 별도 범위다. 작업 브랜치는 #54의 검증된 커밋을 기반으로 하며 #54 자체는 수정하지 않는다.

## 검증

- JDBC 검사: 상태 구분, 제품 범위, 정확한 만료 경계, 원천 부재·컬럼 추가 후 재조회.
- 일반 설정 HTTP: 정상 게시, 멱등 재시도, 거래·이전 차단과 초안 보존, 원천 미배포 503, 이전 취소 후 게시, 이전 수락 후 예전 소유자 게시 거부.
- 별도 PostgreSQL: 정식 Flyway+P2 원천, 게시·외부 이전 동시 요청의 상호 배제. 외부 AI를 호출하지 않는다.

2026-10-29 검증 결과:

- `spotlessCheck test build` 성공. 전체 803개 중 738개 성공, 환경 조건으로 65개 제외, 실패 0개.
- 별도 PostgreSQL DB에서 게시 검사 HTTP 11개, 정식 소유권 제약 3개, P2 구매 요청 15개, P3 거래 검토 17개로 총 46개 모두 성공했다. 테스트 DB는 제거했다.
- 동시 요청 검사는 두 HTTP 요청이 같은 제품의 실제 DB 잠금에서 모두 대기하는 것을 확인한 뒤 잠금을 풀어 검증한다. 일반 테스트에서는 이 PostgreSQL 전용 검사 1개를 제외한다.
