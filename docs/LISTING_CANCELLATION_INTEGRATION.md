# R07 판매중지·예약 거래·내부 이전 취소 연결

판매중지의 거래 처리는 기존 `TradeListingCanceller`와 `TradeCancellationService`를 재사용한다. 새 `JdbcInternalTransferCancellation`은 정식 `ownership_transfers`에 연결되며 시험 취소 포트가 아니다. 거래 기능이 꺼졌을 때 성공하던 기본 대체 처리는 이제 503으로 거부한다.

## 같은 트랜잭션의 처리 순서

1. `ListingManagementService.cancel`이 판매자·현재 소유권·내용 버전을 확인하고 제품→판매글을 잠근다.
2. 판매글을 CANCELLED로 저장하고 `active_slot`을 해제한다.
3. `TradeListingCanceller`가 구매 요청을 ID 순서로 잠근다. 완료된 거래는 거부한다.
4. RESERVED이면 선택 거래의 제품·구매 요청·양측 사용자와 일치하는 INTERNAL/PENDING 이전 **한 건만** 취소한다. `pending_slot=NULL`, `cancelled_at`을 같은 DB에서 기록한다. DIRECT·다른 거래·이미 종료된 이전·누락된 이전은 성공으로 처리하지 않는다.
5. 예약 거래와 남은 PENDING 구매 요청을 취소한다. 판매글을 ACTIVE로 되돌리지 않는다.
6. 열린 판매글이 없는지 확인하고 이력 비공개·판매중지 감사 기록을 저장한다.

어느 단계든 실패하면 판매글·요청·이전·감사를 모두 롤백한다. 이전 SQL 장애는 503 `TRADE_002`, 이전 대상 불일치·누락은 409 `TRADE_001`이다. 같은 판매중지를 재요청하면 기존 결과를 반환하고 최초 취소 시각·사유·감사 기록을 바꾸지 않는다. 새 판매글이나 새 이전 요청도 건드리지 않는다.

## 취소 사유와 화면

```json
{
  "version": 0,
  "reason": "구매자와 취소하기로 합의했습니다",
  "tradeReason": "MUTUAL_AGREEMENT"
}
```

`reason`은 판매중지 감사용 자유문장이다. RESERVED의 `tradeReason`은 `SELF_CIRCUMSTANCES`, `MUTUAL_AGREEMENT`, `COUNTERPART_UNREACHABLE`, `CONDITION_MISMATCH` 중 하나다. ACTIVE에는 선택값이 필요 없다. 기존 클라이언트가 `reason`에 정확한 enum 이름을 보내는 방식은 호환한다. RESERVED의 사유를 선택하지 않고 자유문장만 보내면 임의로 분류하지 않고 400을 반환한다.

판매글 관리 화면은 RESERVED에서만 거래 취소 사유를 선택하게 한다. 자유문장 사유와 선택값을 각각 전송하며, 실패 시 입력을 보존한다.

## 이력·링크의 공개 범위

정식 `product_events`에는 `visibility` 컬럼이 없다. 현행 P4와 같이 공개 범위는 현재 소유권과 ACTIVE/RESERVED 판매글에서 파생된다. 샘플의 visibility 컬럼을 정식 스키마에 추가하거나 정식 이력을 변경하지 않는다.

`JdbcListingHistoryPublisher`는 게시 때 실제 소유권과 열린 판매글을 확인한다. `JdbcListingHistoryPrivatizer`는 중지된 글과 열린 판매글 부재를 같은 제품 잠금 안에서 검증한다. 종료된 글의 상세·대표 사진·선택 사진·AI 요약 API는 차단되고, 현재 소유자의 원본 이력 조회는 유지된다. 이전 상태가 CANCELLED이면 기존 토큰은 검증 응답의 `canAccept=false`이고 수락 요청은 410이다. 기존 이력·증빙·사진·채팅·판매글 기록을 지우지 않는다.

## 실행 조건과 범위

- `app.features.trade-purchase-requests.enabled=true`, `app.features.trade-p3.enabled=true`와 정식 소유권 스키마 및 P2/P3 거래 DDL이 필요하다. 기본 플래그를 켜거나 pending DDL을 일반 마이그레이션으로 옮기지 않는다.
- 실제 개발 DB·기존 8080 서버는 변경하지 않는다. 검증은 별도 PostgreSQL DB에서만 pending DDL을 명시적으로 적용한다.
- 시연 프로필은 기존 샘플 전용 처리를 유지한다. 정식 이력은 공개 검토가 끝난 본문만 노출한다는 기존 Reader 정책을 유지한다.
- 소유권 이전 완료의 P4 연결, 이전 완료 후 제품 버전·AI 갱신과 R11~R12 질의응답은 이 작업의 범위가 아니다.

## 내 판매글 조회와 관리 진입

`GET /api/v1/my-listings`는 인증된 판매자 본인의 ACTIVE/RESERVED/SOLD/CANCELLED 글을 최신 게시 순으로 조회한다. `status`, `page`, `size`로 필터·페이지를 지정하며 판매자 ID는 JWT에서만 결정한다. 공개 마켓은 기존처럼 판매 중인 글만 제공한다.

상단 내 판매글 메뉴, 마켓 상단의 내 판매글 관리, 마이페이지, 상세 화면에서 진입한다. 목록의 관리하기는 기존 상세·관리 API로 바로 연결된다. 종료되거나 현재 소유권·제품 보관 상태 때문에 관리할 수 없는 글은 상태 기록만 표시하고 관리 버튼과 사진 URL을 제공하지 않는다. 다른 소유자의 현재 제품 정보는 포함하지 않는다. 화면 이탈·계정 전환 시 요청과 비공개 목록을 정리한다.

## 검증 범위

SQL 단위 검사는 대상 식별자·이전 유형·종료 상태·만료 PENDING 정리·하위 실패 롤백·스키마 장애를 확인한다. PostgreSQL HTTP 검사는 실제 서비스·정식 테이블·실제 취소 포트를 사용해 정상 취소, 토큰 무효화, 늦은 감사 실패까지의 전체 롤백, 권한·버전·사유 검증, 재판매·새 이전 발급 후 과거 재시도, 동시 중복 요청을 확인한다. 외부 AI 호출이나 시험 취소 포트로 성공을 대체하지 않는다. 실제 브라우저 수동 확인은 별도로 구분한다.

2026-10-30 검증 결과:

- `spotlessCheck test build` 성공. 전체 836개 중 753개 성공, 환경 조건으로 83개 제외, 실패 0개.
- 최신 별도 PostgreSQL 실행에서 실제 취소 HTTP와 내 판매글 권한·응답 검사 18개를 모두 통과했다. 시험 DB는 제거했다. 이전 단계의 게시 검사·정식 소유권 제약·P2/P3 회귀와 구분하며, 새 취소 HTTP는 실제 정식 취소 어댑터를 사용한다.
- 내 판매글 SQL 검사는 본인 범위, 상태별 건수, 페이지 정렬, 종료 기록, 소유권 이전·보관·삭제된 사진의 접근 제한을 확인한다.
- `node --check` 성공. 실제 화면 스크립트를 DOM·네트워크 대역으로 실행해 ACTIVE 요청 형식, RESERVED 필수 선택과 요청 형식, 요청 실패 시 사유 입력 보존을 확인했다.
- 실제 브라우저에서 내 판매글 진입·관리 폼 바로 열기·목록 복귀·상태 필터·새로고침 유지·빈 결과를 확인했다. 데스크톱 1440px, 태블릿 768px, 모바일 390px에서 표시를 확인했다. 사용자가 일반 판매글 중지를 완료한 DB 상태와 예약 글 유지 상태도 확인했다. 예약 글의 판매중지 직접 클릭 시연은 아직 수행하지 않았으며 자동 HTTP 검사와 구분한다.
- 별도 서버 준비 중 실제 P2 수락 경로에서 기본 이전 writer의 `Instant` JDBC 바인딩 오류를 확인해 `Timestamp`로 변환했다. 실제 P2 수락→예약→판매중지 회귀를 위 PostgreSQL 검사에 포함했다.

작업 브랜치는 #58의 게시 검사 코드를 기반으로 한다. 기존 개발 DB·8080 서버는 변경하지 않았다. 수동 확인을 위해 별도로 복제한 DB·Redis와 18082 서버에만 필요한 DDL·플래그를 적용하고 ACTIVE·RESERVED 예제를 준비했다. 검증용 계정·설정·덤프·이미지와 로컬 실행 파일은 저장소에 업로드하지 않는다. 거래 DDL·기능 플래그 적용 조건과 #58의 병합을 확인한 뒤 이 후속 변경을 병합한다.
