# Git 협업 컨벤션

> 본 문서는 Pastport의 브랜치·커밋·PR·코드 리뷰 기준을 정의한다.

> 팀 검토 후 새로운 작업부터 적용하며, 이미 공유·병합한 커밋을 형식에 맞추기 위해 소급 수정하지 않는다.

## 1. 브랜치와 작업 흐름

- 원본 저장소의 최신 `main`을 기준으로 개인 포크에 작업 브랜치를 만들고, 작업 후 원본 저장소의 `main`으로 PR을 보낸다.

  ```text
  최신 main 확인
  → 개인 포크에 작업 브랜치 생성
  → 구현·검증·커밋
  → 원본 main으로 PR
  → 리뷰·CI 확인
  → 병합
  ```

- **브랜치 이름**
  - `<종류>/<작업-내용>` 형식으로 작성한다.
  - 영문 소문자와 하이픈을 사용하고, 작업 목적이 드러나도록 한다.
    - 예시

      ```text
      feature/product-register
      fix/auth-token
      refactor/document-service
      test/product-service
      docs/api-spec
      chore/ci-workflow
      ```

- **브랜치 구분**
  - `feature`: 기능 추가
  - `fix`: 오류 수정
  - `refactor`: 기능 변경 없는 구조 개선
  - `test`: 테스트 작업
  - `docs`: 문서 작업
  - `chore`: 설정·빌드·자동화 등 관리 작업

- **작업 단위**
  - 하나의 기능 또는 논리적인 작업 단위로 브랜치를 만든다.
  - `main`에 직접 push하지 않으며, 다른 팀원의 브랜치와 공동 브랜치에 강제 push하지 않는다.
  - 최신 변경 반영이나 충돌 해결 과정에서 다른 사람의 작업을 덮어쓰지 않는다.

## 2. 커밋 작성

### 2-1. 기본 형식

- [Conventional Commits](https://www.conventionalcommits.org/ko/v1.0.0/)를 기반으로 작성하며, 팀에서는 작업 영역을 나타내는 `scope`를 포함한다.

  ```text
  <type>(<scope>): <subject>
  ```

  - 예시

    ```text
    feat(product): 제품 등록 API 구현
    fix(auth): JWT 만료 처리 오류 수정
    refactor(trade): 거래 상태 검증 로직 분리
    test(document): 문서 업로드 테스트 추가
    docs(api): Swagger API 명세 수정
    ```

- **`type`**
  - 변경의 주된 목적에 따라 선택한다.

- **`scope`**
  - 변경한 도메인이나 공통 영역을 영문 소문자로 작성한다.
  - 예: `auth`, `product`, `document`, `listing`, `trade`, `chat`, `common`, `infra`

- **`subject`**
  - 한국어로 변경 대상과 내용을 작성하고, : 뒤에는 공백 한 칸을 넣는다.
  - 제목 전체는 50자 내외를 권장하며, 끝에 마침표를 붙이지 않는다.
  - 수정, 작업 완료, `update`처럼 변경 내용을 알 수 없는 제목은 피한다.

### 2-2. 커밋 타입

- `feat`: 새로운 기능·화면 추가

- `fix`: 버그·잘못된 동작 수정

- `refactor`: 기능 변경 없는 구조 개선

- `docs`: 문서 추가·수정

- `test`: 테스트 추가·수정

- `style`: 동작에 영향 없는 공백·줄바꿈·코드 포맷 정리

- `chore`: 다른 타입에 해당하지 않는 관리 작업

- `build`: 빌드·의존성 변경

- `ci`: CI·CD 설정 변경

- `perf`: 성능 개선

### 2-3. 변경 단위와 본문

- **하나의 논리적 변경**
  - 한 커밋에는 하나의 목적을 담는다.
  - 같은 기능에 필요한 테스트·설정·Flyway 마이그레이션은 함께 포함할 수 있으며, 관련 없는 변경은 분리한다.

- **변경 이유**
  - 제목만으로 설명하기 어려우면 빈 줄 아래에 변경 이유와 영향을 작성한다.
  - 관련 이슈가 있으면 `Refs: #12`처럼 연결한다.

    ```text
    fix(auth): 만료된 JWT 요청의 오류 응답 통일

    인증 필터의 만료 예외를 공통 오류 응답으로 처리한다.

    Refs: #12
    ```

- **호환성이 깨지는 변경**
  - 기존 API·설정의 사용 방식이 달라지면 `feat(api)!: ...`처럼 !를 표시한다.
  - 본문이나 `BREAKING CHANGE:` 항목에 영향과 필요한 대응을 설명한다.

- **자동 생성 메시지**
  - Git 도구가 자동 생성하는 병합·되돌리기 메시지는 기본 형식 적용에서 제외한다.
  - 되돌릴 때는 대상 커밋과 이유를 확인할 수 있도록 남긴다.

## 3. PR과 코드 리뷰

### 3-1. PR 작성

- **제목**
  - 커밋과 같은 `<type>(<scope>): <subject>` 형식을 사용한다.

- **작업 범위**
  - 하나의 기능 또는 논리적 작업 단위로 작성한다.
  - 다른 PR에 의존하면 해당 PR과 검토 순서를 명시한다.

- **설명**
  - 작업 내용, 변경 이유, 테스트 결과, 확인이 필요한 사항을 작성한다.
  - API·DB·화면이 바뀌면 관련 명세·마이그레이션·화면 자료를 함께 제공한다.
    - 작업 내용: 무엇을 구현하거나 변경했는지
    - 변경 이유: 왜 필요한 변경인지
    - 테스트 결과: 실행한 검사와 결과 · 실행하지 못한 항목과 이유
    - 확인 사항: 리뷰 시 확인할 내용 · 연관 이슈, PR과 주의사항

- **공통 코드 변경**
  - 인증·보안 설정, 공통 응답·예외, 환경 설정 등 여러 기능에 영향을 주는 변경은 작업 전에 관련 팀원에게 공유한다.
  - 변경 범위를 이해하는 팀원에게 리뷰를 요청한다.

### 3-2. 리뷰 진행

- 리뷰에는 대상 위치와 이유를 함께 적는다. 작성자는 의견에 답하고 필요한 수정을 반영하며, 승인 후 주요 내용이 바뀌면 변경 부분을 다시 확인받는다.
  - **[수정 필수]**
    - 오류·요구사항 위반·보안·데이터 일관성 문제에 사용한다.
    - 수정하거나 논의를 통해 문제가 해소된 뒤 병합한다.
  - **[제안]**
    - 가독성·구조 개선 의견에 사용한다.
    - 작성자는 반영 여부와 이유를 답한다.
  - **[질문]**
    - 구현 의도나 동작 확인이 필요할 때 사용한다.

- **CodeRabbit 활용**
  - AI 리뷰는 보조 검토에 활용하고, 실제 코드와 요구사항을 기준으로 판단한다.
  - AI 리뷰만으로 팀원의 코드 리뷰 승인을 대신하지 않는다.

## 4. 병합 조건과 마무리

다음 조건을 모두 충족한 뒤 병합한다.

1. 작성자 외 팀원 최소 1명에게 승인받는다.
2. 변경에 적용되는 필수 CI의 형식 검사·빌드·자동 테스트가 통과한다.
3. 수정 필수 의견과 병합 충돌이 해소된다.

실행할 CI 항목은 프로젝트 설정을 기준으로 한다. 충돌은 PR 작성자가 해결하고, 해결 과정에서 변경한 내용도 필요한 검증을 다시 수행한다.

- **병합 방식**
  - Squash Merge를 권장한다.
  - 최종 커밋 제목은 PR 제목의 컨벤션을 유지하고, 필요한 변경 이유와 이슈 연결을 남긴다.

- **브랜치 정리**
  - 병합한 원격 작업 브랜치는 소유자가 후속 작업·의존 PR이 없는지 확인한 뒤 삭제한다.
  - 다음 작업은 원본 저장소의 최신 `main`을 기준으로 새 브랜치에서 시작한다.
