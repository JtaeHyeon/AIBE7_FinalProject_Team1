# Flyway 버전 번호 정리안

## 팀에서 맞출 기준

실사용 DB에 자동 적용하지 않는 검증안이다. 먼저 적용된 요약 갱신 버전 `2026102701`을 기준으로 제안한다. 같은 SQL을 이름만 바꾼 `2706` 적용 DB는 백업 후 적용 기록의 버전·스크립트 이름만 맞춘다. 실제 데이터나 SQL 체크섬은 변경하지 않는다.

| 내용 | 현재 main | 정리안 |
| --- | --- | --- |
| 요약 갱신 | `2026102706` | 원래 `2026102701` 복원 |
| 소유권 테이블 | `2026102702` | `2026102803` |
| 소유권 대기 슬롯 | `2026102707` | `2026102804` |

세 SQL의 내용은 그대로 유지한다. 예전 시연 DB에 적용된 카드 형식 `2702`도 그대로 둔다. 새 소유권 버전은 기존 일반 DB의 최신 `2802` 뒤에서 실행되므로 `outOfOrder`를 켜지 않는다.

## 실행 순서

1. 팀이 번호 기준과 소유권 구버전의 적용 여부를 확인한다. `2702__create_ownership_tables` 또는 `2707__add_ownership_pending_slot`을 이미 적용했다면 이 절차를 중단하고 별도로 검토한다.
2. 각 서버를 멈추고 해당 DB의 전체 백업을 만든다. 백업을 별도 DB에 복원할 수 있는지 먼저 확인한다.
3. `2701` 적용 DB는 번호 정규화가 필요 없다. `2706` 적용 DB만 아래 조건 검사를 통과한 경우 한 번 정규화한다.
4. 정리한 코드로 Flyway validate/migrate를 실행한다. 새 소유권 테이블과 대기 슬롯이 `2803`, `2804`로 적용되는지 확인한다.
5. 기존 사용자·제품·이력·판매글 데이터와 로그인·이력 조회를 확인한다. 실패하면 애플리케이션을 계속 멈추고 백업과 기록을 기준으로 검토한다.

새 DB는 정리된 코드만 실행하면 된다. 예전 H2 시연 DB는 이 PostgreSQL 스크립트를 실행하지 않는다. `2701`·시연 `2702` 기록을 유지한 채 복사본에서 업그레이드를 확인한다.

## 2706 적용 DB의 조건부 정규화

`scripts/db/normalize-summary-version.psql`은 자동 마이그레이션 폴더 밖에 있다. `psql`에서 DB명과 스키마를 명시한다. 연결 대상과 다르면 실패하고, 일치하더라도 아래 조건이 충족되지 않으면 트랜잭션을 롤백한다.

- `2701`과 `2706` 중 정확히 하나만 존재한다.
- 성공한 SQL이며 체크섬 `620449880`, 설명과 파일 이름이 검증된 요약 SQL과 일치한다.
- 실제 요약 시각 컬럼 두 개와 해당 상태 제약이 존재한다.
- 기존 소유권 버전 `2702`, `2707` 적용 기록이 없다.

통과한 `2706` 행의 `version`, `script` 두 필드만 바꾼다. `installed_rank`, 설치 시각, 실행 시간, 체크섬 등 나머지 기록과 업무 데이터는 유지한다. 이미 정상인 `2701`에 다시 실행하면 변경하지 않는다.

PostgreSQL 클라이언트가 있는 환경의 실행 형식:

```text
psql -d 실제DB명 -U 실제사용자 -v expected_database=실제DB명 -v expected_schema=public -f scripts/db/normalize-summary-version.psql
```

로그인 비밀번호는 채팅·코드·명령 인자에 넣지 않는다. Docker 안에서 실행할 때는 두 파일을 같은 디렉터리에 복사하고 그곳의 `.psql`을 사용한다. 이 명령은 백업과 팀 합의가 끝난 뒤 대상 DB 담당자가 실행한다.

Flyway `repair`는 버전 번호를 바꿔 주는 명령이 아니다. [공식 이름 변경 설명](https://documentation.red-gate.com/fd/tutorial-renaming-a-migration-script-192840442.html)은 적용 후 번호를 바꿨다면 각 DB의 버전 기록 조정이 필요함과 백업의 필요성을 설명한다. [repair 설명](https://documentation.red-gate.com/flyway/reference/commands/repair)은 체크섬·설명·타입 정렬 등의 범위를 안내한다.

## 검증

새 일반 DB, 예전 시연 DB 업그레이드, `2701` 유지, `2706` 정규화 후 업그레이드를 검사한다. 잘못된 DB·스키마·체크섬, 두 번호 동시 존재, 미완료 DDL과 소유권 구버전 적용은 거부하고 기존 기록을 보존하는지 PostgreSQL 테스트로 확인한다.

- `spotlessCheck test build` 통과. 전체 743개 중 698개 성공, 환경 조건으로 45개 제외, 실패·오류 없음.
- 별도 PostgreSQL DB에서 조건 검사·롤백·업그레이드 9개 모두 성공. 위 전체 검사에서 제외된 PostgreSQL 전용 검사도 별도로 실행한 결과다.
- 실제 로컬 PostgreSQL 백업을 복원한 `2701` 복사본, 같은 복사본에서 기록을 `2706`으로 재현한 DB, 기존 H2 시연 파일 복사본이 모두 `2804`까지 migrate/validate를 통과했다. 각 복사본의 기존 17개 업무 테이블을 원래 컬럼 기준으로 비교해 데이터 보존을 확인했다.
- 에이전트의 검증 과정에서는 사용 중인 로컬 PostgreSQL에 변경을 실행하지 않았고 H2 원본 파일 해시도 동일하다. 임시 PostgreSQL 검증 DB는 제거했으며 백업과 검증 기록은 로컬에 보관했다.

실제 팀원 DB의 전체 백업을 받지 않았으므로 `2706` 재현은 동일 체크섬의 검증된 SQL을 적용한 격리 DB에서 수행한다. 개별 DB의 다른 미공유 변경까지 확인한 것은 아니다.
