## **1. users (회원)**

**테이블 역할**

회원가입과 로그인에 필요한 정보를 관리한다. 제품 소유자·이력 작성자·거래 참여자를 같은 회원 번호로 연결하는 기준이다.

**컬럼**

- id (필수, PK): 회원을 구분하는 고유번호.
- email (필수, UQ): 가입과 로그인에 사용하는 이메일.
- password\_hash (필수): 로그인 검증에 사용하는 비밀번호 해시값. 비밀번호 원문은 저장하지 않는다.
- nickname (필수): 프로필과 판매글 등에 표시하는 이름.
- email\_verified\_at (선택): 이메일 인증을 완료한 시각. 인증 전에는 비어 있다.
- role (필수, 기본값 USER): 서비스 접근 권한을 구분한다. 일반 회원은 USER, 관리자는 ADMIN을 사용한다. 제품별 판매자·구매자·소유자 관계와는 별개다.

**핵심 제약**

- 이메일은 정해진 기준으로 정리한 뒤 중복을 막는다.
- 이메일 인증을 완료해야 로그인할 수 있다.
- 판매자·구매자·소유자는 회원의 고정 등급이 아니라 제품·거래와의 관계로 판단한다.
- role에는 USER, ADMIN만 저장할 수 있다.

**관련 요구사항:** AUTH-01 · AUTH-02 · AUTH-05 · ADM-01

## **2. products (제품)**

**테이블 역할**

실물 제품 한 대의 기본 정보와 현재 소유자를 관리한다. 소유자가 바뀌어도 같은 제품 번호에 사진·증빙·이력이 계속 연결된다.

**컬럼**

- id (필수, PK): 실물 제품 한 대를 구분하는 고유번호.
- current\_owner\_id (필수, FK → users.id): 현재 소유자의 회원 번호. 제품 관리와 증빙 조회 권한을 판단한다.
- category (필수): 제품 종류. 현재 범위에서는 LAPTOP을 사용한다.
- name (필수): 사용자가 제품을 알아보기 쉽게 정한 이름.
- manufacturer (필수): 제품 제조사.
- model\_name (필수): 제조사가 정한 모델명 또는 모델 번호.
- serial\_number (필수): 실물을 식별하는 시리얼 번호.
- first\_purchase\_on (선택): 제품을 처음 구매한 날짜. 현재 소유자의 사용 시작일과는 구분한다.
- warranty\_expires\_on (선택): 확인된 보증 만료일. 현재 보증 유효 여부를 계산하는 기준이다.
- warranty\_terms (선택): ‘구매 후 2년’과 같은 보증 조건.
- facts\_version (필수): 제품 정보·사양·핵심 이력이 변경될 때 증가하는 버전 번호.

    - 예를 들어 버전 7에서 거래 완료를 확인한 뒤 수리 이력이 추가돼 버전 8이 되면, 양측이 최신 내용을 다시 확인해야 한다.

**설계 이유**

- 현재 소유자와 작성자를 구분한다. 소유권을 이전받았다고 이전 소유자가 입력한 값의 정정 권한까지 생기지는 않는다. 항목별 작성자는 product\_field\_authors에서 확인한다.
- facts\_version으로 확인 대상의 최신성을 판단한다. 버전 7에서 거래 완료를 확인한 뒤 새 이력이 추가돼 버전 8이 되면 다시 확인받아야 한다. AI 결과가 최신 제품 사실을 기준으로 작성됐는지도 이 번호로 검사한다.
- 보증 만료일과 보증 조건을 함께 둔다. 구매일을 몰라 만료일을 계산하지 못하더라도, 문서에서 확인한 보증 조건은 보관할 수 있어야 한다.

**핵심 제약**

- 제조사와 시리얼 번호의 조합은 중복될 수 없다.
- 제품마다 현재 소유자는 한 명이며, 소유권 이전 후에도 제품 번호를 유지한다.
- 기본 정보 정정은 현재 소유자가 본인이 입력한 값에 대해서만 할 수 있다.
- 시리얼 번호는 현재 소유자에게만 제공한다.

**관련 요구사항:** PROD-01 · PROD-02 · PROD-03 · PROD-06 · PROD-07 · PROD-08

## **3. laptop\_specs (노트북 기준 사양)**

**테이블 역할**

노트북을 처음 등록할 때의 기준 사양을 보관한다. 이후 유효한 사양 변경 이력을 적용해 현재 사양을 계산한다.

**컬럼**

- product\_id (필수, PK, FK → products.id): 기준 사양이 속한 제품 번호.
- initial\_cpu (선택): 처음 등록한 CPU 모델·사양.
- initial\_ram\_gb (선택): 처음 등록한 RAM 용량. 단위는 GB다.
- initial\_storage (선택): 처음 등록한 저장장치 구성. 예: SSD 512GB + HDD 1TB.
- initial\_gpu (선택): 처음 등록한 GPU 모델·사양.
- initial\_display (선택): 처음 등록한 화면 크기·해상도 등 화면 사양.
- initial\_os (선택): 처음 등록한 운영체제.
- initial\_battery\_status (선택): 처음 등록할 때 확인한 배터리 상태.

**설계 이유**

- 기준 사양과 변경 이력을 함께 사용한다. 처음 8GB였던 RAM을 16GB로 교체한 이력이 무효 처리되면, 기준 사양과 남은 유효 이력으로 현재 사양을 다시 계산할 수 있다.

**핵심 제약**

- 제품 번호를 기본키로 사용하므로 제품당 기준 사양은 하나다.
- 확인하지 않은 사양은 비워 두며, RAM 용량을 입력하면 1GB 이상이어야 한다.
- 현재 사양은 기준 사양에 유효한 VALID 이력의 변경 항목을 발생일·등록 시각·이력 번호 순으로 적용한다. 무효인 VOID 이력은 제외한다.

**관련 요구사항:** PROD-04 · HIST-06

## **4. product\_images (제품 사진)**

**테이블 역할**

제품 외관 사진의 파일 정보와 제품 화면의 대표 사진·표시 순서를 관리한다. 초안과 판매글에서는 저장된 사진 중 필요한 사진을 선택해 사용한다.

**컬럼**

- id (필수, PK): 사진 한 장을 구분하는 고유번호.
- product\_id (필수, FK → products.id): 사진이 속한 제품 번호.
- object\_key (필수, UQ): 파일 저장소에서 사진을 찾는 경로·키.
- content\_type (필수): 서버가 검사한 이미지 파일 형식.
- byte\_size (필수): 저장된 파일의 실제 크기. 단위는 바이트다.
- sort\_order (필수): 해당 제품 안에서 사진을 보여줄 순서.

    - **0 이상의 정수를 사용하며 작은 값부터 표시한다. 같은 대상 안에서는 순서가 중복될 수 없다.**
- is\_primary (필수): 제품 화면의 대표 사진 여부.

**핵심 제약**

- 제품 안에서 사진 순서는 중복될 수 없고 0 이상이어야 한다.
- 제품의 대표 사진은 최대 한 장이다.
- 제품 화면의 사진 순서·대표 선택은 초안과 판매글의 선택과 별도로 관리한다.
- 영수증·수리 명세서 등의 증빙은 documents에서 관리한다.

**관련 요구사항:** PROD-05 · SALE-01

## **5. product\_field\_authors (기본 정보 작성자)**

**테이블 역할**

제품 기본 정보의 항목별 작성자를 기록한다. 제품명은 A가, 비어 있던 구매일은 B가 입력한 경우처럼 항목마다 작성자가 달라도 정정 권한을 구분할 수 있다.

**컬럼**

- product\_id (필수, 복합 PK, FK → products.id): 작성자를 관리할 제품 번호.
- field\_name (필수, 복합 PK): 작성자를 기록할 항목 이름. 예: name, first\_purchase\_on.
- author\_id (필수, FK → users.id): 해당 값을 처음 입력·확정한 회원 번호.

**핵심 제약**

- 제품 번호와 항목 이름의 조합은 중복될 수 없다.
- 실제 값은 products에 저장하고, 이 테이블에는 작성자만 기록한다.
- 기존 값 정정은 현재 소유자·항목 작성자·로그인 회원이 모두 같을 때 허용한다.
- 소유권이 이전돼도 기존 항목의 작성자는 바꾸지 않는다.
- 지정된 기본 정보 항목만 등록할 수 있다. 작성자 기록이 있다는 이유로 정정 가능한 항목이 늘어나지는 않는다.

**관련 요구사항:** PROD-08 · DOC-04

## **6. documents (증빙 문서)**

**테이블 역할**

개인정보를 가리고 확인한 증빙 사본의 파일 정보와 열람·삭제 제한을 관리한다. AI 또는 수동 입력으로 해당 문서의 제품 사실을 이미 확정했는지도 기록한다.

**컬럼**

- id (필수, PK): 증빙 문서의 고유번호. 재마스킹으로 사본을 교체해도 유지한다.
- product\_id (필수, FK → products.id): 증빙이 속한 제품 번호.
- uploader\_id (필수, FK → users.id): 처음 업로드한 회원 번호.
- object\_key (필수, UQ): 마스킹을 확인한 사본의 비공개 저장소 경로·키.
- content\_type (필수): 서버가 검사한 사본의 파일 형식.
- byte\_size (필수): 저장된 사본의 실제 크기. 단위는 바이트다.
- version (필수): 재마스킹으로 사본을 교체할 때 증가하는 문서 버전.
- mask\_confirmed\_at (필수): 사용자가 현재 사본의 마스킹 상태를 확인한 시각.
- redaction\_required\_at (선택): 개인정보 누락을 발견한 시각. 값이 있으면 사본 제공과 AI 처리를 차단한다.
- protected\_at (선택): 이력 연결·소유권 이전으로 삭제 보호가 시작된 시각.
- facts\_confirmed\_at (조건부): AI 후보 또는 수동 입력을 제품 사실로 확정한 시각.

**설계 이유**

- 최초 업로더와 삭제 보호를 함께 확인한다. 현재 소유자라도 이전받은 증빙은 직접 삭제할 수 없다. 한 번 보호된 문서는 이력 연결을 해제하거나 원래 소유자에게 돌아와도 보호를 유지한다.
- 사실 확정 여부는 문서에 둔다. AI를 사용하지 않고 수동으로 확정할 수도 있기 때문이다. facts\_confirmed\_at은 재요청·재마스킹으로 같은 사실이나 이력이 중복 생성되는 것을 막는다.

**핵심 제약**

- 사용자가 마스킹을 확인한 JPG·PNG·PDF 사본만 저장하며 최대 10MB다.
- 원본과 마스킹 전 내용은 서버 저장·AI 전송 대상에서 제외한다.
- 열람·다운로드마다 현재 소유권을 검사한다. 개인정보 누락으로 차단된 문서는 확인한 교체 사본을 저장한 뒤에만 차단을 해제한다.
- 직접 삭제는 현재 소유자이면서 최초 업로더이고, protected\_at이 비어 있을 때만 허용한다.
- 재마스킹으로 사본을 교체해도 이미 확정한 사실과 삭제 보호는 유지한다.

**관련 요구사항:** DOC-01 · DOC-04 · DOC-06 · DOC-07 · HIST-08

## **7. document\_extractions (문서 AI 추출)**

**테이블 역할**

문서 AI 분석의 동의·진행 상태·추출 후보를 관리한다. AI를 이용한 문서에만 기록을 만들며, 문서당 현재 분석 기록을 최대 하나 보관한다.

**컬럼**

- document\_id (필수, PK, FK → documents.id): 분석 대상 문서 번호.
- document\_version (필수): 이번 분석에 사용한 사본 버전.
- requested\_by\_id (필수, FK → users.id): 분석을 요청하고 외부 전송에 동의한 회원 번호.
- consent\_at (필수): 이번 분석의 외부 전송에 동의한 시각.
- consent\_notice\_version (필수): 동의받은 처리 목적·외부 전송 안내문의 버전.
- status (필수): 분석 대기 QUEUED, 처리 중 PROCESSING, 검토 가능 EXTRACTED, 실패 FAILED, 사실 확정 CONFIRMED.
- attempt\_id (필수): 분석 시도마다 새로 만드는 UUID.
- extracted\_facts (조건부): 사용자가 검토할 추출 후보를 임시 보관하는 JSON.
- error\_code (조건부): 분석 실패를 안내할 안전한 오류 코드.
- updated\_at (필수): 현재 분석 상태가 마지막으로 바뀐 시각.

**설계 이유**

- 파일 관리와 AI 처리를 분리한다. 사본 저장과 외부 AI 분석은 별도 단계이므로, AI를 사용하지 않은 문서에 분석 관련 값을 채울 필요가 없다.
- 사본 버전과 분석 시도를 따로 구분한다. 사본을 바꾸면 document\_version으로, 같은 사본을 재분석하면 attempt\_id로 구분한다. 이전 작업의 늦은 응답이 최신 결과를 덮어쓰지 못하게 한다.

**핵심 제약**

- 문서당 현재 분석 기록은 최대 하나이며, 재시도는 같은 기록의 시도 번호를 바꾼다.
- 결과 반영 전 사본 버전·시도 번호·처리 중 상태·문서 미확정 여부·차단 여부·요청자의 현재 소유권을 다시 검사한다.
- EXTRACTED에는 검토 후보가 필요하다. AI 후보를 사실로 확정할 때 제품 반영·문서 확정 시각·CONFIRMED 전환을 함께 처리하고 후보는 비운다.
- 수동 확정·재마스킹·개인정보 차단은 미확정 AI 작업을 무효화한다. 이미 확정한 사실과 분석 출처는 유지한다.
- 오류 코드에 내부 오류 원문이나 증빙 내용을 저장하지 않는다.

**관련 요구사항:** DOC-02 · DOC-03 · DOC-04 · DOC-05 · AI-08

## **8. product\_events (제품 이력)**

**테이블 역할**

제품에 발생한 구매·점검·수리·부품 교체·사양 변경·소유권 이전을 사건별로 기록한다. 소유자가 바뀌어도 같은 제품에 이력이 누적된다.

**컬럼**

- id (필수, PK): 사건 하나를 구분하는 고유번호.
- product\_id (필수, FK → products.id): 사건이 발생한 제품 번호.
- author\_id (조건부, FK → users.id): 일반 이력을 작성한 회원 번호. 시스템 이전 이력은 비워 둔다.
- event\_type (필수): 구매 PURCHASE, 점검 INSPECTION, 수리 REPAIR, 부품 교체 PART\_REPLACEMENT, 사양 변경 SPEC\_CHANGE, 이전 TRANSFER.
- occurred\_on (필수): 사건이 실제로 발생한 날짜.
- title (필수): 사건을 짧게 설명하는 제목.
- content (선택): 사건의 구체적인 제품 사실·작업 내용.
- service\_provider (선택): 구매처·수리처·점검처 등 업체 정보.
- cost (선택): 확인된 구매·수리·점검 비용. 원 단위 정수이며 공개 이력에서는 제외한다.
- replaced\_part (선택): 실제로 교체한 부품.
- specs\_before (조건부): 사양이 바뀐 항목의 변경 전 값을 담은 JSON.

    - RAM을 8GB에서 16GB로 교체했다면 RAM 8GB를 기록한다.
- specs\_after (조건부): 같은 항목의 변경 후 값을 담은 JSON.

    - 위 사례에서는 RAM 16GB를 기록하며, 유효한 이력의 변경값을 현재 사양 계산에 반영한다.
- status (필수): 유효 VALID 또는 무효 VOID.
- transfer\_request\_id (조건부, FK → ownership\_transfers.id, UQ): 시스템 이전 이력의 원인이 된 요청 번호.
- created\_at (필수): 서버에 이력을 등록한 시각. 실제 발생일과 구분한다.

**설계 이유**

- 부품 교체와 사양 변경을 구분한다. 같은 사양의 배터리로 교체하는 경우처럼, 부품을 교체해도 사양은 달라지지 않을 수 있다.
- 변경 전후 사양은 바뀐 항목만 기록한다. 당시 어떤 값에서 어떤 값으로 바뀌었는지 설명하고, 유효한 변경을 순서대로 적용해 현재 사양을 계산한다.

**핵심 제약**

- 일반 이력에는 작성자가 필요하고 이전 요청 번호는 비워 둔다. 시스템 TRANSFER 이력은 작성자를 비우고 이전 요청 번호를 필수로 연결한다.
- 이전 요청 번호의 고유 제약으로 같은 이전의 자동 이력이 중복 생성되는 것을 막는다.
- 기존 이력은 직접 삭제하지 않고 정정 또는 VOID 처리한다. 현재 소유자는 본인이 작성한 일반 이력만 정정할 수 있으며, 변경 전후 내용과 사유를 audit\_logs에 남긴다.
- 예약 중에는 기존 정보 정정을 막고, 새로 발생한 점검·수리·교체·사양 변경만 추가한다. 추가 시 구매자 변경 확인 항목을 만들고 양측 완료 확인을 초기화한다.
- 무효 이력의 존재는 유지하되 현재 사양과 유효 사건 집계에서는 제외한다. 공개 내용에는 비용·시리얼·개인정보·증빙의 존재나 파일을 포함하지 않는다.

## **12. listings (판매글)**

**테이블 역할**

게시된 판매 조건·진행 상태·AI 요약을 관리한다. 채팅과 구매 요청이 연결되는 기준이며, 재판매할 때는 새 판매글을 만들어 과거 거래와 구분한다.

**컬럼**

- id (필수, PK): 판매글을 구분하는 고유번호.
- product\_id (필수, FK → products.id): 판매 대상 제품 번호.
- seller\_id (필수, FK → users.id): 게시 당시 판매자의 회원 번호.
- title (필수): 판매글 제목.
- price (필수): 판매글에 표시한 가격. 원 단위 정수다.
- condition\_grade (필수): 판매자가 제품 상태를 보고 직접 선택한 1\~5등급. AI가 자동 판정한 등급은 아니다.
- description (필수): 판매 설명.
- status (필수): 판매 중 ACTIVE, 예약 중 RESERVED, 판매 완료 SOLD, 취소 CANCELLED.
- content\_version (필수): 판매글 내용이 바뀔 때 증가하는 버전 번호.
- published\_at (필수): 판매글을 게시한 시각.
- summary\_text (조건부): 공개 가능한 제품 사실과 판매 조건으로 만든 AI 요약문.
- summary\_source\_product\_version (조건부): 요약 생성에 사용한 products.facts\_version.
- summary\_source\_listing\_version (조건부): 요약 생성에 사용한 content\_version.
- summary\_status (조건부): 요약 생성의 대기·진행·완료·실패 상태.

    - 비어 있음: 요약 생성 요청 전.  / QUEUED: 생성 요청을 접수하고 대기 중. / PROCESSING: 요약 생성 중. / READY: 요약 생성 완료. / FAILED: 요약 생성 실패.
- summary\_attempt\_id (조건부): 요약 생성 시도마다 새로 만드는 UUID.
- summary\_error\_code (조건부): 요약 생성 실패를 안내할 안전한 오류 코드.
- summary\_updated\_at (조건부): 요약 처리 상태가 마지막으로 바뀐 시각.

**설계 이유**

- 판매자는 게시 당시 회원으로 유지한다. 제품의 현재 소유자가 바뀌어도 과거 판매글·채팅·거래의 당사자가 바뀌면 안 된다.
- 요약의 제품 버전과 판매글 버전을 따로 기록한다. 제품 이력이 바뀌거나 판매 가격·설명이 바뀌면 요약이 오래된 내용이 될 수 있다. 같은 버전으로 재시도한 작업은 시도 번호로 구분한다.

**핵심 제약**

- 한 제품에 ACTIVE 또는 RESERVED 판매글은 최대 하나다.
- 게시 시 제목·가격·등급·설명과 대표 사진이 필요하다. 가격은 1원 이상 정수, 등급은 1\~5여야 한다.
- R05 물리 구현은 동시 중복 게시 방어를 위해 `active_slot`(ACTIVE/RESERVED=1, 종료=NULL)과 `(product_id, active_slot)` 고유 제약을 사용한다. `source_draft_id`·`source_draft_version`은 삭제된 초안의 게시 재시도를 식별하는 내부 보조 값이며 FK가 아니다.
- 예약 중에는 판매 조건 변경을 막는다. SOLD·CANCELLED 글은 보존하며 수정·재공개하지 않는다.
- 일반 목록에는 ACTIVE 글을 제공한다. 로그인한 상세 조회는 ACTIVE·RESERVED 글에 제공하고, 판매 종료 시 일반 공개와 공개 AI 제공을 종료한다.
- AI 결과는 제품 버전·판매글 버전·현재 시도를 검사해 반영한다. 재생성 중에는 기존 요약에 최신화 중임을 표시하며, 오래된 응답이 덮어쓰지 못하게 한다.

**관련 요구사항:** SALE-01 · SALE-02 · SALE-05 · SALE-06 · SALE-07 · AI-03

## **14. chat\_rooms (채팅방)**

- 새 채팅방은 로그인한 다른 회원이 ACTIVE 판매글에 문의할 때 만든다. 자신의 판매글에는 문의할 수 없다.
- 거래 종료·소유권 이전 후에도 원래 판매자와 문의자만 기존 대화를 사용한다.
- 마지막 확인 순번은 0부터 해당 방의 실제 마지막 메시지 순번 사이이며, 이전 값보다 작아질 수 없다.
- 확인 순번은 본인의 미확인 표시용으로 사용한다. 상대방에게 읽음 여부를 제공하는 용도로 사용하지 않는다.

구매 요청 한 번과 수락 이후의 예약·취소·완료를 관리한다. 요청당 거래가 최대 하나이므로 같은 기록에서 요청 상태와 거래 상태를 구분한다.

**컬럼**

- id (필수, PK): 구매 요청과 그 요청에서 이어진 거래의 고유번호.
- room\_id (필수, FK → chat\_rooms.id): 구매 요청을 보낸 채팅방 번호.
- listing\_id (필수, FK → listings.id): 구매 요청의 대상 판매글 번호.
- request\_status (필수): 요청 대기 PENDING, 수락 ACCEPTED, 거절 REJECTED, 취소 CANCELLED.
- transaction\_status (조건부): 수락 후 예약 RESERVED, 완료 COMPLETED, 취소 CANCELLED. 수락된 적 없는 요청은 비워 둔다.
- seller\_confirmed\_version (조건부): 판매자가 거래 완료 버튼을 누르며 확인한 제품 버전.
- buyer\_confirmed\_version (조건부): 선택 구매자가 거래 완료 버튼을 누르며 확인한 제품 버전.
- cancelled\_by\_id (조건부, FK → users.id): 예약을 취소한 판매자 또는 선택 구매자의 회원 번호.
- cancel\_reason (조건부): 수락 후 예약을 취소할 때 취소자가 선택한 사유. 다음 중 하나를 저장한다.

    - SELF\_CIRCUMSTANCES: 내 사정으로 취소 — 일정·마음 변경 등.
    - MUTUAL\_AGREEMENT: 상대 요청으로 합의하여 취소.
    - COUNTERPART\_UNREACHABLE: 상대 연락 두절.
    - CONDITION\_MISMATCH: 제품 상태가 설명과 다름.
- cancelled\_at (조건부): 예약 취소가 확정된 시각.

**설계 이유**

- listing\_id를 직접 저장한다. 채팅방에서도 판매글을 찾을 수 있지만, DB에서 판매글당 예약 거래를 하나로 제한하기 위해 함께 저장한다. 두 판매글 번호가 같은지도 검사한다.
- 완료 여부 대신 확인한 제품 버전을 저장한다. 새 이력이 추가되면 이전 내용에 대한 완료 확인을 구분하고 양측에 다시 확인받아야 한다.

**핵심 제약**

- 한 채팅방의 PENDING 요청과 한 판매글의 RESERVED 거래는 각각 최대 하나다. 재요청은 새 기록으로 구분한다.
- 수락 전에는 거래 상태를 비운다. 수락 시 ACCEPTED/RESERVED, 완료 시 ACCEPTED/COMPLETED, 예약 취소 시 CANCELLED/CANCELLED가 된다.
- 요청 하나를 수락해도 다른 대기 요청은 유지한다. 거래가 완료되면 다른 대기 요청은 거절한다.
- 완료하려면 양측 확인 버전이 현재 facts\_version과 같고 구매자의 미확인 변경이 없어야 한다. 새 이력이 생기면 양측 확인을 초기화한다.
- 예약 취소 시 취소자·사유·시각이 모두 필요하다. 판매글을 ACTIVE로 돌리고 내부 이전도 취소하되 다른 대기 요청은 유지한다.
- 예약은 시간이 지났다는 이유로 자동 취소하지 않는다.

**관련 요구사항:** TX-03 · TX-04 · TX-05 · TX-06 · OWN-01 · ADM-02

## **17. transaction\_change\_reviews (예약 중 변경 확인)**

**테이블 역할**

예약 중 추가된 이력의 변경 내용과 선택 구매자의 확인 결과를 보존한다. 변경이 여러 번 발생해도 각각 확인할 수 있도록 사건별로 기록한다.

**컬럼**

- purchase\_request\_id (필수, 복합 PK, FK → purchase\_requests.id): 변경 확인이 필요한 예약의 구매 요청 번호.
- event\_id (필수, 복합 PK, FK → product\_events.id): 예약 중 새로 추가된 이력 번호.
- change\_facts (필수): 예약 중 추가돼 구매자에게 안내한 당시의 변경 내용을 보존하는 JSON 사본.

    - 예를 들어 예약 후 RAM을 8GB에서 16GB로 교체했다면, 교체 사건과 사양 변경 내용을 남긴다. 이후 원이력이 정정돼도 구매자가 당시 확인한 내용은 유지한다.
- decision (조건부): 선택 구매자의 예약 유지 KEEP 또는 취소 CANCEL. 응답 전에는 비어 있다.
- reviewed\_at (조건부): 구매자가 해당 변경에 응답한 시각.

**설계 이유**

- 당시 변경 내용을 사본으로 남긴다. 나중에 원이력이 정정되더라도 구매자가 무엇을 보고 예약 유지·취소를 결정했는지 확인할 수 있어야 한다.

**핵심 제약**

- 구매 요청과 추가 이력의 조합은 중복될 수 없다. 같은 제품의 예약 중 새로 추가된 사건만 연결한다.
- 선택 구매자만 응답할 수 있다. 미응답일 때 결정·확인 시각은 모두 비우고, 응답하면 함께 저장한다.
- KEEP는 예약 유지이며 거래 완료 버튼을 대신하지 않는다.
- CANCEL은 예약 취소와 함께 처리한다. 이미 등록한 이력과 사양 변경은 유지한다.
- 보존 범위는 예약 중 추가된 변경과 응답 결과·시각이다. 예약 시작 당시의 전체 판매 조건·사양·이력 사본은 저장하지 않는다.

**관련 요구사항:** HIST-05 · TX-05 · TX-06

## **18. ownership\_transfers (소유권 이전 요청)**

**테이블 역할**

어떤 제품을 누구에게서 누구에게 넘기는지와 이전 진행 상태를 관리한다. 내부 거래를 통한 이전과 외부 링크·QR 이전을 함께 처리한다.

**컬럼**

- id (필수, PK): 소유권 이전 요청을 구분하는 고유번호.
- product\_id (필수, FK → products.id): 이전할 제품 번호.
- transfer\_type (필수): 내부 거래 INTERNAL 또는 외부 이전 EXTERNAL.
- purchase\_request\_id (조건부, FK → purchase\_requests.id, UQ): 내부 이전의 원인이 된 수락된 구매 요청 번호.
- from\_user\_id (필수, FK → users.id): 이전 요청을 발급한 당시 소유자의 회원 번호.
- to\_user\_id (조건부, FK → users.id): 내부 거래의 선택 구매자 또는 외부 이전의 확인된 수신자.
- status (필수): 대기 PENDING, 완료 ACCEPTED, 취소 CANCELLED, 외부 만료 EXPIRED.
- token\_hash (조건부, UQ): 외부 링크·QR에 사용하는 일회성 토큰의 해시값.
- recipient\_approved\_at (조건부): 외부 수신자가 이전을 수락한 시각.
- owner\_approved\_at (조건부): 소유자가 확인된 외부 수신자에게 이전을 승인한 시각.
- created\_at (필수): 이전 요청을 생성한 시각. 외부 요청의 만료를 계산하는 기준이다.

**설계 이유**

- 구매 요청과 이전 요청을 분리한다. 외부 이전은 판매글·구매 요청 없이도 가능하므로, 이전 절차를 독립적으로 관리해야 한다.
- 외부 이전은 수신자 확인과 소유자 승인을 구분한다. 링크 발급이나 접속만으로 소유권이 바뀌지 않도록 양측의 명시적 승인을 확인한다.

**핵심 제약**

- 제품당 PENDING 이전 요청은 최대 하나다. 완료 직전에도 발급자가 현재 소유자인지 검사한다.
- 내부 요청은 구매 요청 수락 시 생성하고 선택 구매자를 연결한다. 양측의 최신 거래 완료 버튼으로 이전하며 토큰·외부 승인 시각은 비워 둔다.
- 외부 요청은 구매 요청 없이 토큰 해시를 저장한다. 진행 중 판매글·예약이 있으면 발급하지 않으며, 생성 후 24시간이 되는 시점부터 사용할 수 없다.
- 외부 수신자는 발급자와 달라야 하며, 한 번 확인된 수신자는 바꾸지 않는다. 수신자 확인 후 소유자가 승인하고 양측 승인 조건을 충족해야 완료한다.
- 이전 진행 중 제품 사실·사진 변경을 제한한다. 완료·취소·만료된 요청과 토큰은 재사용하지 않는다.
- 완료 시 소유자 변경·자동 이전 이력 하나·증빙 보호·초안 삭제·변경 기록을 함께 반영한다. 내부 거래는 거래 COMPLETED와 판매글 SOLD도 함께 처리한다.

**관련 요구사항:** OWN-01 · OWN-02 · OWN-03 · OWN-04 · OWN-05 · OWN-06

## **19. audit\_logs (변경·정정 기록)**

**테이블 역할**

확정된 업무 변경의 처리자·대상·시각을 기록한다. 제품 정보나 이력을 정정할 때 변경 전후 내용과 사유를 보존한다.

**컬럼**

- id (필수, PK): 변경 기록을 구분하는 고유번호.
- product\_id (필수, FK → products.id): 변경이 발생한 제품 번호.
- actor\_id (조건부, FK → users.id): 변경을 처리한 회원 번호. 시스템 처리이면 비워 둔다.
- target\_id (필수): 처리 대상의 번호. 대상 테이블은 action으로 판단하며, 거래 대상은 purchase\_requests.id를 사용한다.
- event\_id (조건부, FK → product\_events.id): 정정·무효 처리한 원이력 번호.
- before\_facts (조건부): 정정 직전의 사실을 보존한 JSON.
- after\_facts (조건부): 정정·무효 처리 직후의 사실을 보존한 JSON.
- reason (조건부): 이력·기본 정보 정정 또는 무효 처리의 사유.
- action (필수): 게시·정정·취소·완료·이전 등 처리한 행위.
- result (필수): 확정된 업무 변경의 처리 결과인 SUCCESS.
- created\_at (필수): 해당 변경이 확정된 시각.

**설계 이유**

- target\_id와 event\_id는 역할이 다르다. target\_id는 판매글·거래·이전 등 여러 종류의 대상을 기록하므로 단일 FK를 걸지 않는다. 이력 정정은 event\_id를 따로 연결해 원이력과의 관계를 FK로 보장한다.
- 변경 전후 내용을 보존한다. 현재값만 수정하면 원래 값과 중간 정정 과정이 사라지므로, 각 정정 당시의 내용과 사유를 남긴다.

**핵심 제약**

- 기록은 추가만 하며 기존 기록을 수정·삭제하지 않는다. 이력 정정 기록은 제품 이력과 함께 보존한다.
- 이력 정정·무효 처리에는 처리 회원·원이력·변경 전후 내용·사유가 필요하다. 이때 target\_id와 event\_id는 같아야 한다.
- 기본 정보 정정에도 변경 전후 내용과 사유가 필요하다.
- action에 맞는 실제 대상인지, 해당 대상이 같은 제품에 속하는지 검사한다. 공개 전환 방향은 VISIBILITY\_PUBLIC·VISIBILITY\_PRIVATE로 기록한다.
- 전체 감사 기록은 별도 권한으로 관리한다. 타임라인에 제공하는 정정 내역에는 공개 범위와 개인정보 제외 규칙을 적용한다.

**관련 요구사항:** PROD-08 · HIST-04 · HIST-06 · HIST-08 · SEC-08 · ADM-03 · ADM-04
