# 코딩 컨벤션

> 본 문서는 Pastport의 코드 작성과 구현 기준을 정의한다.

> 기능·권한·데이터 구조는 요구사항 정의서·ERD·API 명세를 따르며, 협업 방식은 Git 협업 컨벤션을 따른다.

> 팀 검토 후 새로 작성하거나 수정하는 코드부터 적용한다.

## 1. 네이밍과 코드 스타일

| 대상 | 기준 | 예시 |
| --- | --- | --- |
| 클래스 | `UpperCamelCase`<br>역할이 드러나는 이름 | `ProductService` |
| 메서드 | `lowerCamelCase`<br>수행하는 동작 표현 | `registerProduct` |
| 변수·필드 | `lowerCamelCase`<br>담고 있는 값 표현 | `productId`, `currentOwner` |
| Boolean 판단 메서드 | is · has · can으로 의미 표현 | `isProtected`, `canCancel` |
| 상수·열거형 값 | `UPPER_SNAKE_CASE` | `MAX_FILE_SIZE`, `PENDING` |
| 패키지 | 영문 소문자 | `product`, `repository` |
| 요청·응답 `DTO` | `Request`·`Response` 접미사 | `CreateProductRequest`, `ProductResponse` |

- 의미를 알기 어려운 축약어는 피한다. `ID` · `DTO` · `JWT`처럼 통용되는 약어는 사용할 수 있다.

- Java의 들여쓰기 · 줄바꿈 · import 정렬은 프로젝트의 Spotless 설정을 따른다.

- 사용하지 않는 import와 줄 끝 공백을 제거하고, 파일 인코딩은 UTF-8을 사용한다.

- 자동 포맷은 `./gradlew spotlessApply`로 실행한다.

- HTML·CSS·JavaScript는 기존 파일의 스타일과 공통 모듈을 우선 사용한다.

- 의미 있는 제한값은 상수나 설정값으로 관리한다. 정해진 상태·유형은 `Enum` 등으로 표현하고 DB·API의 값과 일치시킨다.

- 주석은 코드만으로 알기 어려운 이유·제약·주의사항을 설명한다. 임시 구현에는 남겨둔 이유와 후속 작업을 기록한다.

## 2. 패키지 구조와 계층 책임

기능·도메인별로 패키지를 나누고, 각 도메인 안에서 계층을 구분한다.

```text
{domain}
├── controller
├── service
├── repository
├── entity
└── dto

common
```

- **Controller**
  - 요청을 받고 입력 검증과 응답 처리를 담당한다.
  - 비즈니스 로직을 작성하거나 Repository를 직접 호출하지 않는다.

- **Service**
  - 업무 처리 순서, 권한 검사와 트랜잭션 범위를 관리한다.
  - 여러 데이터의 변경이 필요한 기능은 Service에서 전체 흐름을 조정한다.

- **Repository**
  - 데이터 저장·조회와 필요한 쿼리를 담당한다.

- **Entity**
  - 자신의 상태와 상태 변경 규칙을 관리한다.
  - 상태 변경은 `confirm()`·`cancel()`처럼 의미가 드러나는 메서드로 표현한다.

- **`DTO`**
  - API 요청·응답에 필요한 데이터를 전달한다.
  - Entity를 API 응답으로 직접 반환하지 않는다.

- **공통 구현**
  - 의존성은 생성자로 주입하고, 여러 도메인에서 실제로 공유하는 기능만 `common`에 둔다.
  - 다른 도메인과 연동할 때는 기존에 제공하는 서비스·조회 인터페이스를 우선 사용한다.
  - 기존 구조를 존중하며, 작업과 무관한 패키지 이동·일괄 리팩터링·불필요한 추상화는 하지 않는다.

## 3. API·DTO·예외 처리

- **API 경로**
  - `/api/v1` 아래에서 소문자·하이픈과 복수형 자원명을 사용한다.
  - 검색·정렬·페이지 조건은 쿼리 파라미터로 전달한다.
    - 예: `/api/v1/products`, `/api/v1/purchase-requests`

- **HTTP 메서드**
  - 조회는 `GET`, 생성은 `POST`, 전체 수정은 `PUT`, 부분 수정은 `PATCH`, 삭제는 `DELETE`를 기본으로 한다.
  - 수락·취소·완료 같은 업무 행위는 API 명세에 정한 별도 경로를 사용한다.

- **입력 검증**
  - 필수 여부·형식·길이·범위는 요청 `DTO`에서 검증한다.
  - 소유권·처리 가능한 상태·연결된 데이터의 유효성은 Service·Entity에서도 검증한다.

- **성공 응답**
  - 일반적인 데이터 응답은 기존 `ApiResponse<T>`를 사용한다.
  - `204`는 응답 본문을 보내지 않으며, 파일 응답은 해당 API 명세를 따른다.
  - `DTO`에는 해당 기능과 사용자의 권한에 필요한 정보만 포함한다.

```json
{
  "success": true,
  "data": {
    "id": 1
  }
}
```

- **예외 처리**
  - 업무 예외는 기존 `CommonException`·`ErrorCode`를 사용하고, `GlobalExceptionHandler`에서 공통 처리한다.
  - 오류 응답은 기존 `ErrorResponse` 구조를 사용한다.
  - 예외를 잡고 무시하거나, 실패한 작업을 성공으로 응답하지 않는다.
  - **오류 응답 항목**
    - `timestamp`: 발생 시각
    - `status`: HTTP 상태 코드
    - `code`: 서비스 오류 코드
    - `message`: 사용자에게 제공할 안내
    - `path`: 요청 경로
    - `requestId`: 요청 추적 번호
    - `fieldErrors`: 입력 항목별 검증 오류

- **HTTP 상태 코드**
  - 기능별 구체적인 응답과 오류 코드는 API 명세를 따른다. 자원의 존재를 숨겨야 하는 경우에는 명세에 따라 `404`를 사용할 수 있다.
    - `200`: 조회·처리 성공
    - `201`: 자원 생성 성공
    - `204`: 응답 본문이 없는 처리 성공
    - `400`: 잘못된 요청·입력값
    - `401`: 인증 정보 없음·만료·무효
    - `403`: 인증된 사용자의 권한 부족
    - `404`: 자원 없음
    - `409`: 중복 요청·현재 상태와의 충돌
    - `413`: 허용 크기 초과
    - `429`: 요청 횟수 제한 초과
    - `500`: 예상하지 못한 서버 오류
    - `503`: 의존 서비스·저장소의 일시적 이용 불가

## 4. DB·JPA·트랜잭션

- **테이블·컬럼**
  - 이름은 ERD를 기준으로 하며, `snake_case`와 복수형 테이블명을 사용한다.
  - 외래키는 `{대상}_id`, 날짜는 `_on`, 시각은 `_at`을 기본으로 한다.
  - Entity·마이그레이션·ERD가 일치하도록 관리하고, 기능에 필요하지 않은 컬럼·관계를 추가하지 않는다.

- **Flyway 마이그레이션**
  - 스키마 변경은 새 마이그레이션 파일로 추가한다.
  - 기존 파일을 임의로 수정·이름 변경하거나, `ddl-auto=update`로 스키마를 맞추지 않는다.
  - 새 파일은 기존 최대 버전보다 크고 다른 작업과 중복되지 않아야 한다.

```text
V{yyyyMMdd}{두 자리 순번}__{설명}.sql

예: V2026101901__add_listing_status.sql
```

- **JPA 연관관계·조회**
  - Lazy Loading을 기본으로 하고, 필요한 방향의 연관관계만 매핑한다.
  - N+1 발생 여부를 확인하고, 필요한 조회에 Fetch Join · EntityGraph 등을 적용한다.
  - 목록 조회에는 페이지 구분이나 조회 수 제한을 적용한다.

- **날짜·시각**
  - 날짜는 `LocalDate`, 처리 시각은 `Instant`를 기본으로 사용한다.
  - 시각은 UTC 기준으로 다루고 화면에 표시할 때 필요한 시간대로 변환한다.

- **트랜잭션**
  - Service에서 경계를 관리하며, 쓰기는 `@Transactional`, 순수 조회는 `@Transactional(readOnly = true)`를 기본으로 한다.
  - 함께 성공하거나 실패해야 하는 DB 변경은 하나의 트랜잭션으로 처리한다.
  - 외부 API 응답을 기다리며 DB 트랜잭션을 장시간 유지하지 않도록 한다.

- **상태 변경·동시 요청**
  - 상태 변경 가능 여부와 권한을 서버에서 검증한다.
  - 중복·동시 요청에도 데이터가 일치하도록 DB 제약, 잠금, 조건부 갱신 등을 필요한 범위에서 적용한다.
  - 화면의 버튼 제한이나 DB의 상태값 범위 검사만으로 업무 조건을 대신하지 않는다.

## 5. 보안과 로깅

- **인증·권한**
  - 사용자는 검증된 인증 정보로 식별한다.
  - 요청에 담긴 사용자 `ID`만 신뢰하지 않고, 대상 데이터의 접근·변경 권한을 서버에서 확인한다.

- **비밀정보**
  - 비밀번호·토큰·비밀 키·API 키를 코드와 로그에 남기지 않는다.
  - `.env` 등 비밀정보가 담긴 파일은 커밋하지 않고, 환경변수나 서버 설정으로 관리한다.
  - 비밀번호는 단방향 해시로 저장하고, Refresh Token은 기존 Redis 관리 방식을 따른다.

- **입력·파일 보호**
  - SQL에 사용자 입력을 문자열로 직접 결합하지 않는다.
  - 사용자 입력·AI 응답을 표시할 때 임의의 HTML·스크립트가 실행되지 않도록 한다.
  - 파일의 권한·허용 종류·실제 형식·크기를 검증하고, 증빙 원본과 마스킹 전 내용은 요구사항의 전송·저장 제한을 따른다.

- **로그 작성**
  - SLF4J Logger를 사용하며, `System.out`·`printStackTrace()`로 운영 로그를 남기지 않는다.
  - 오류 종류·요청 `ID` 등 추적에 필요한 정보를 기록하고, 같은 오류를 여러 계층에서 중복 기록하지 않는다.
  - 개인정보·파일 내용·채팅·AI 입출력 원문과 비밀정보는 기록하지 않는다.

| 수준 | 사용 기준 |
| --- | --- |
| `DEBUG` | 개발·문제 분석에 필요한 상세 정보 |
| `INFO` | 주요 정상 처리 |
| `WARN` | 복구 가능하지만 확인이 필요한 상황 |
| `ERROR` | 예상하지 못한 오류·처리 실패 |

- **오류 정보·업무 기록**
  - 사용자 응답에는 내부 오류 추적 내용이나 서버 설정을 노출하지 않는다.
  - 업무 변경 기록과 운영 오류 로그는 각각의 목적에 맞게 관리한다.

## 6. 테스트와 작업 완료 기준

- **테스트 작성 범위**
  - 새 기능과 주요 비즈니스 로직에는 테스트를 작성한다.
  - 정상 동작과 함께 권한 오류·잘못된 입력·중복 요청·허용되지 않은 상태 변경을 확인한다.
  - 데이터 일관성에 영향을 주는 동시 처리도 검증한다.

- **테스트 종류**
  - 업무 규칙은 단위 테스트로 확인하고, 외부 의존성은 Mock 등으로 분리한다.
  - DB 제약·실제 쿼리·트랜잭션·동시성이 중요한 기능은 PostgreSQL 기반 통합 테스트로 확인한다.
  - API 변경 시 요청 검증·응답 형식·HTTP 상태 코드도 확인한다.

- **이름과 구성**
  - 클래스명은 `ProductServiceTest`, `ChatRepositoryIntegrationTest`처럼 대상과 종류를 표현한다.
  - 메서드명은 조건과 예상 결과가 드러나도록 작성하며, 한글·영문 모두 허용한다.
  - 테스트는 준비 → 실행 → 검증 순서로 작성하고, JUnit 5와 필요한 경우 Mockito를 사용한다.

- **관련 문서**
  - 구현 변경에 따라 API 명세·ERD·요구사항·주석의 수정이 필요한지 확인한다.
  - 새로운 의존성을 추가하기 전에는 기존 구현과 의존성으로 해결할 수 있는지 확인한다.

- **완료 검증**
  - 아래 검사를 실행하고 결과를 PR에 기록한다.
  - 실행하지 못한 항목은 이유와 함께 명시하며, 미실행 검사를 통과했다고 보고하지 않는다.

```bash
./gradlew spotlessCheck
./gradlew test
./gradlew build
```

자동 포맷이 필요하면 `./gradlew spotlessApply`를 실행한다.
