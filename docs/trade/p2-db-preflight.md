# P2 Stage B DB 사전점검 안내

## 상태와 목적

- 상태: `NOT_RUN` (2026-10-26)
- 목적: 정식 ownership 연결과 pending 거래 DDL 편입 전에 구조·Migration 이력·legacy 연결 후보를 읽기 전용으로 확인한다.
- 범위: 승인된 담당자가 `p2-db-preflight.sql`을 수동 실행할 때 사용할 입력, 선택 기준, 판정표다.
- 비범위: DDL/DML, Flyway `repair`·`baseline`·`clean`, 자동 복구, 애플리케이션 기동, 공유 환경 접속 승인을 대신하지 않는다.

읽기 전용 조회도 실제 대상 DB 접속과 업무 데이터 조회이므로 별도 승인을 받은 뒤 실행한다. 저장소 `.env`, 기존 개발
접속값, CI 비밀값을 자동으로 사용하지 않는다.

## 실행 전 입력과 승인

| 항목 | 입력 |
|---|---|
| 대상 환경·DB | 미정 |
| 대상 스키마 | 미정 (`REPLACE_WITH_APPROVED_SCHEMA`를 승인된 값으로 직접 변경) |
| 승인 담당자·승인 근거 | 미정 |
| 실행 담당자·시각 | 미정 |
| 허용 조회 범위 | 메타데이터와 승인된 집계 쿼리 |
| 실행 결과 | `NOT_RUN` |

1. 대상 환경, DB 이름, 스키마, 읽기 권한, 승인 근거를 먼저 기록한다.
2. 접속 명령은 승인된 운영 절차에서 별도로 제공한다. 문서에 비밀번호·토큰·접속 문자열을 기록하지 않는다.
3. SQL 상단의 `target_database`, `target_schema`를 직접 입력한다. DB 이름이 다르면 템플릿은 종료한다.
4. 먼저 메타데이터 절만 실행한다. `statement_timeout=10s`, `lock_timeout=2s`, 읽기 전용 트랜잭션을 완화하지 않는다.
5. 확인된 테이블과 컬럼에 대응하는 주석 처리 집계 절만 하나씩 선택한다. `<TARGET_SCHEMA>`는 확인된 식별자로 직접 치환하며 문자열 입력이나 셸 치환으로 조립하지 않는다.
6. 오류·권한 부족·타임아웃은 0건이나 정상으로 기록하지 않고 별도 판정한다.

## 저장소 기준 예상 순서

| 구분 | 저장소 자료 | 현재 판정 |
|---|---|---|
| 일반 SQL Migration | `db/migration`의 `V5`, `V2026101201`~`V2026102101` | 저장소 순서만 확인, 실제 적용 이력 미확인 |
| 일반 Java Migration | `V2026102102__isolate_published_listing_ids` | 저장소 존재, 실제 적용 이력 미확인 |
| 거래 pending DDL | `db/pending/trade-p2/V2026102103__create_purchase_requests.sql` | 일반 Flyway 경로 밖, 편입 미승인 |
| ownership DDL | 미제공 | 객체·버전·의존 방향 미확정 |

`flyway_schema_history` 조회 결과와 수동 DDL 적용 여부가 제공되기 전에는 새 적용 버전이나
`purchase_requests`·ownership의 최종 순서를 확정하지 않는다.

## 판정표

| 판정 | 의미 | 다음 조치 |
|---|---|---|
| 실행 안 함 | 승인 또는 실행이 없고 결과가 없음 | `NOT_RUN` 유지 |
| 구조 미확인 | 권한 부족, 오류, 타임아웃 등으로 구조를 판단할 수 없음 | 원인과 승인 범위를 확인한 뒤 재조회 |
| 객체 없음 | 메타데이터 조회는 성공했으나 대상 객체가 없음 | 누락 사실 기록, 자동 생성 금지 |
| 일치 후보 | 키·판매자·초안 ID 등의 집계상 후보가 있음 | 의미상 매핑 근거를 별도 검토 |
| 불일치 | FK 후보, 판매자, 방/게시글 관계가 현재 계약과 다름 | 영향 건수와 원인을 기록하고 승인 요청 |
| 업무 의미 미확인 | 숫자 ID나 판매자가 같지만 의미상 연결 근거가 없음 | 연결로 확정하거나 자동 보정하지 않음 |

`객체 없음`, `권한 때문에 안 보임`, `조회 안 함`은 서로 다른 결과다. `source_draft_id_candidates`와
`ambiguous_numeric_matches`도 정식 게시글 연결을 입증하지 않는다.

## 결과 기록 원칙

- 결과에는 대상 식별, 실행한 절, 시작·종료 시각, 쿼리 성공 여부, 건수와 판정만 기록한다.
- 채팅 본문, 이메일, 증빙 내용, 토큰, 비밀번호를 조회하거나 결과에 남기지 않는다.
- 개별 ID 목록은 후속 조치 승인에 꼭 필요한 경우 별도 범위와 보관 방법을 승인받은 뒤 다룬다.
- 정합화 필요 시 매핑 근거, 영향 건수, dry-run, 백업, 복구, 승인 순서를 먼저 문서화한다.
- 이 자료에는 UPDATE·DELETE 또는 자동 repair 스크립트를 추가하지 않는다.

## 재개 조건

1. 승인된 DB·스키마·읽기 권한과 실행 담당자가 정해지면 메타데이터 점검을 수행한다.
2. 정식 ownership DDL·제약·담당 승인·기준 SHA가 제공되면 포트 계약과 실제 구조를 대조한다.
3. Migration 이력과 legacy 집계 결과가 확보되면 충돌 없는 편입 버전과 fresh/upgrade 시험 순서를 확정한다.
4. 실제 변경은 영향·백업·복구 승인을 별도로 받은 후 새 Migration으로 수행한다.
