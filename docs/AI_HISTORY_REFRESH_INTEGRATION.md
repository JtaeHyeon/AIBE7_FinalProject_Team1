# 실제 제품 이력 변경 후 AI 요약 갱신

## 연결 범위

`HistoryService.create/correct/voidEvent`가 이력·증빙·감사 기록과 제품 사실 버전을 같은 트랜잭션에서 저장하고 `ProductFactsChanged(productId)`를 발행한다. 기존 R10 `ListingSummaryRefreshListener`는 커밋 후 ACTIVE·RESERVED 판매글의 새 요약을 별도 트랜잭션으로 접수한다. 외부 AI는 이력 저장 요청에서 호출하지 않는다.

- 일반 점검·수리·구매·사양을 바꾸지 않는 부품 교체 이력 추가에도 `facts_version`이 1 증가한다.
- 사양 저장·재계산 경로는 저장소가 이미 버전을 증가시킨다. 추가·정정·무효 처리마다 정확히 1 증가하며 서비스에서 중복 증가시키지 않는다.
- 권한·상태 검증에 실패하거나 트랜잭션이 롤백되면 갱신 요청을 접수하지 않는다.
- 커밋 뒤 갱신 접수 장애나 이후 모델 실패가 성공한 이력 저장을 되돌리지 않는다. 놓친 접수는 기존 R10 조정기가 제품 버전 차이로 복구할 수 있다.
- 새 요약은 실제 이력 Reader의 최신 허용 자료를 사용한다. 미검토 본문·비용·증빙·사유는 AI 입력에서 계속 제외하며, 생성 중 다시 변경되면 이전 작업이 최신 시도를 덮어쓰지 못한다.
- H2에서 문자열로 반환하는 사양 스냅샷은 정정 시 JSON 객체로 정규화해 반복 저장의 중복 인코딩을 방지한다. 원래 사양 값은 보존한다.

## 실행과 확인

새 마이그레이션이나 의존성은 없다. 기존 `V2026102801`·`V2026102802`가 적용된 DB에서 `LISTING_HISTORY_ENABLED=true`, AI 요약 활성화와 기존 Gemini 설정을 사용한다.

1. 본인 제품에 ACTIVE 또는 RESERVED 판매글과 요약이 있는지 확인한다.
2. 점검 이력을 추가한다. 제품 버전이 1 증가하고 이전 문구가 숨겨진 뒤 새 요약 작업이 접수되는지 확인한다.
3. 같은 이력을 정정하고 무효 처리한다. 각각 버전이 1 증가하며 최신 날짜·정정·무효 정보로 갱신되는지 확인한다.
4. 사양 변경은 추가·정정·무효 처리 시 메모리 등 현재 사양과 버전이 함께 바뀌는지 확인한다.

판매 중인 글이 없으면 이력과 버전만 저장하고 AI를 호출하지 않는다. 실제 이력 원천이 없는 시연 프로필의 샘플 자료와 이 검증을 구분한다. 문서 확정·소유권 이전·공개 범위 변경을 향후 별도 저장 경로에서 구현하면 같은 버전·이벤트 계약을 연결해야 한다.

Swagger 쓰기 요청은 `XSRF-TOKEN` 쿠키를 `X-XSRF-TOKEN` 헤더에 넣는다. 인증 성공 시 기존 CSRF 토큰이 지워지므로 `CsrfCookieFilter`는 `SessionManagementFilter` 뒤에서 새 토큰을 읽는다. 인증 전에 읽으면 응답에서 쿠키가 삭제되어 다음 요청이 403, 재시도가 성공하는 문제가 생긴다. CSRF 검증과 인증 시 토큰 교체는 유지한다. [Spring Security CSRF 문서](https://docs.spring.io/spring-security/reference/7.0/servlet/exploits/csrf.html#csrf-integration-javascript-spa)

## 자동 검증

실제 이력 API·서비스·Flyway·JDBC Reader·커밋 후 리스너·요약 저장소를 연결한다. AI 모델과 Redis 실행권만 테스트 대역으로 대체하며 외부 AI는 호출하지 않는다.

등록·정정·무효·사양 복구의 정확한 버전 증가, 트랜잭션 중 접수 방지와 롤백, 갱신 조회 장애·모델 실패 후 이력 보존, 생성 중 재변경의 이전 결과 차단, 종료된 판매글의 AI 미접수를 검증한다. 브라우저와 같은 쿠키 인증으로 조회·등록·정정·무효를 연속 실행하고 매 응답 뒤 다음 요청용 CSRF 쿠키가 존재하는지 확인한다. CSRF 헤더가 없거나 틀리면 403이며 이력·버전이 변경되지 않는지도 검증한다.

- 변경 작업의 기존 기준에서 `spotlessCheck test`는 전체 651개 중 615개 성공, 환경 조건으로 36개 제외, 실패·오류 없음.
- 최신 main `f5ad102` 통합 후 형식 검사는 통과했고, 전체 744개 중 705개 성공·36개 제외·시연 DB 마이그레이션 3개 실패였다. 수정하지 않은 동일 main에서도 같은 3개 실패를 재현했다. 정식 `V2026102702__create_ownership_tables.sql`과 시연 전용 `V2026102702__version_listing_card_summary.sql`의 버전 중복 문제이며 이 변경의 마이그레이션 수정은 없다. 전체 CI 통과 전에 팀의 버전 충돌 정리가 필요하다.
- 최신 main 통합본의 별도 PostgreSQL DB에서 실제 이력 API·쿠키 CSRF·Reader·기존 요약 흐름 63개 모두 성공. 테스트 DB는 종료 후 제거했다.
- 사용자 개발 DB의 제품 이력·판매글을 테스트용으로 추가하거나 수정하지 않았다. 로컬 DB에 공개 판매글이 없다면 수동 확인은 이력 저장·버전 증가까지 가능하며, 자동 요약은 게시·예약 중인 글이 준비된 뒤 확인한다.

최신 main은 기존 요약 갱신 마이그레이션도 `2026102701`에서 `2026102706`으로 바꾼 상태다. 이미 `2026102701`이 적용된 DB의 업그레이드 정책은 팀과 별도로 맞춰야 한다. 이 작업에서는 기존 개발·시연 DB를 최신 main으로 재기동하거나 Flyway 이력을 수정하지 않았다.
